# Week 12 — Repeatable Deployment Procedure

**Ticket:** CVNP1606-W12-012  
**Tenant:** ACME LAB (sign in with an authorized administrator account; never put credentials in this note).  
**Production goal:** Register new-hire Windows hardware, attach an Autopilot profile, target an Intune configuration policy, and verify first-boot results.  
**Lab policy actually created:** `ACME-W12-ScreenLock` targeted to `ACME-Pilot-Devices`.

1. **Sign in.** Open https://intune.microsoft.com with a licensed account allowed to administer Intune. Select the ACME LAB tenant and open **Devices**. Confirm that the target device and the intended Entra group exist.
2. **Collect each new device's hardware hash.** On an administrator PowerShell session on each device, use the approved `Get-WindowsAutopilotInfo` script to export an Autopilot CSV (for example, `Get-WindowsAutopilotInfo -OutputFile C:\Temp\hashes.csv -GroupTag ACME-Riverside`). An OEM/reseller-provided compatible CSV can be used instead. Create `C:\Temp` first if needed. Handle hardware hashes as company device records.
3. **Register hardware.** In Intune go to **Devices → Windows → Enrollment → Windows Autopilot devices** and **Import** the CSV. Check that the correct serial numbers appear. If the vendor registered the devices already, confirm the records instead of importing duplicates.
4. **Set the group tag and grouping.** Set/verify `ACME-Riverside` on each Autopilot record. Ensure the intended dynamic Entra device group uses this tag to include the newly registered devices. Confirm group membership has populated.
5. **Check the deployment profile.** In **Devices → Windows → Enrollment → Deployment profiles**, use an approved **user-driven / Microsoft Entra join** Autopilot deployment profile for individually assigned new-hire laptops; assign it to the corresponding Autopilot device group. Confirm expected OOBE skips and naming template `ACME-%SERIAL%` if used in this deployment.
6. **Verify Autopilot assignment.** Return to **Windows Autopilot devices** and check every planned serial number reads **Profile status: Assigned**. If it says Unassigned, correct the tag, group membership or profile assignment *before shipping*.
7. **Create the configuration profile.** Open **Devices → Configuration → Create → New policy**; set **Platform: Windows 10 and later**, **Profile type: Settings catalog**. Name it `ACME-W12-ScreenLock`. Description: `Week 12 security policy for automatic screen locking on ACME Windows devices.`
8. **Set the exact security option.** On **Configuration settings → Add settings**, search `Machine Inactivity Limit`, choose **Local Policies Security Options → Interactive Logon Machine Inactivity Limit**, and set **900** (seconds). Do **not** select *Interactive Logon Machine Account Lockout Threshold*; that is a different setting. Capture `W12-03-ScreenLock-Settings.png`.
9. **Target and publish.** Leave default scope tags unless required. On **Assignments → Add groups**, include **ACME-Pilot-Devices** (active device group; the pilot target actually used for this lab), with no additional filter or exclusions. Capture `W12-04-Profile-Assignments.png`. Select **Review + create → Create** and confirm the policy appears under **Devices → Configuration**.
10. **Check Enrollment Status Page.** Under **Devices → Windows → Enrollment → Enrollment Status Page**, review the ESP assigned to the deployment group. For production, configure blocking of desktop access until the specified required setup/apps have installed. Capture actual ESP settings. **This lab's live ESP status has not been verified in the evidence collected so far.**
11. **Test first boot and management.** On a supported, properly registered pilot machine, connect to the network, run OOBE, sign in as the designated test user for user-driven mode, and confirm Entra join and Intune enrollment. Observe the ESP until it completes. Confirm the device name and Intune compliance state. Never treat simulation dashboard data as proof of live deployment.
12. **Verify policy delivery and document release decision.** In Intune select **Devices → All devices → [test device] → Device configuration**. Locate `ACME-W12-ScreenLock` and record the displayed status. If **Pending**, check the device's last check-in and request **Sync** if available; do not claim Succeeded. If **Error/Conflict**, investigate and correct the setting or assignment. Generate the policy assignment-status report if needed. Only a **Succeeded** status on a qualifying, checked-in device confirms this configuration applied. Record the deployment profile, configuration outcome, compliance state, and actual ESP result before approving shipments.

After launching the **separate 1606Midterm VM** and syncing it, Intune showed a new check-in on **November 15 at 4:15 PM**, and the device's **Device configuration** report showed **ACME-W12-ScreenLock: Succeeded**. This confirms the tested configuration profile was applied.
